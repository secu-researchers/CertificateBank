# CertificateBank 개발문서

`.py` 코드의 구조와 계약을 정리한다. 설계 결정과 근거는 `DESIGN.md`, SKILL 규칙은 `skills/`를 따른다. 기준은 현재 소스이며 테스트 코드는 없다.

## 1. 실행과 구성

- 실행: `.venv/Scripts/python.exe app.py`. `app.py`가 `create_app()`을 호출하고 `127.0.0.1:5000`에 바인딩한다.
- 의존성: `Flask>=3.0`, `anthropic>=1.11`.
- `create_app(overrides=None)`: Flask 앱 팩토리. `overrides` dict로 설정을 덮어쓴다.

| 설정 키 | 기본값 |
|---|---|
| `SECRET_KEY` | 기동 시 생성하는 무작위 값. 재시작하면 세션이 무효가 된다 |
| `SKILLS_DIR` | `<프로젝트>/skills` |
| `DATA_DIR` | `<프로젝트>/data` |

| `app.extensions` | 객체 |
|---|---|
| `storage` | `Storage(DATA_DIR)` |
| `keyvault` | `KeyVault()` |
| `jobs` | `JobRegistry()` |

- CSRF: 모든 POST는 폼 필드 `csrf_token`이 세션의 `csrf`와 같아야 하며 아니면 400이다. 템플릿에는 컨텍스트 프로세서가 `csrf_token`을 주입한다.
- Jinja 필터 `question_html` = `render.format_question`.

## 2. 모듈 맵

```
app.py
certbank/
├─ __init__.py       앱 팩토리, CSRF
├─ llm.py            Claude 호출, 모델 목록, 오류 변환
├─ generator.py      배치 생성, 검증 루프, 시험지 저장
├─ grader.py         배치 채점, 총평
├─ schema.py         문항·답안·채점 결과 검증, 통계 계산
├─ qtypes/__init__.py 문항 유형 레지스트리
├─ storage.py        JSON 파일 저장소
├─ skills.py         SKILL 로더
├─ render.py         문항·답안 표시, 토큰 사용량 문자열
├─ stats.py          응시 기록 집계
├─ jobs.py           백그라운드 작업 레지스트리
├─ keyvault.py       API 키 메모리 보관소
└─ routes/           main, settings, generate, exams, grading, history
```

의존 방향(→는 import): `routes` → `generator`·`grader`·`llm`·`storage`·`stats`·`render`·`skills`; `generator`·`grader` → `schema`·`skills`·`render`; `schema` → `qtypes`; `storage` → `schema`. `llm`, `keyvault`, `jobs`, `skills`, `render`는 다른 내부 모듈에 의존하지 않는다.

## 3. 모듈별 명세

### 3.1 llm.py

Claude 호출을 감싼다. 응답은 구조화 출력(JSON 스키마)으로 받아 dict로 파싱한다. API 키는 인자로만 받으며 저장하거나 기록하지 않는다.

- `MODELS`: `ModelOption(id, label, supports_effort)` 튜플. 순서는 Sonnet 5.5(기본), Opus 5.5, Fable 5.1, Haiku 4.5. `MODEL_IDS`, `DEFAULT_MODEL = "claude-sonnet-5-5"`, `EFFORTS = (low, medium, high, xhigh, max)`.
- `LLMError(kind, message)`: 화면에 보여 줄 한국어 메시지를 담는다. `kind`는 `auth`, `permission`, `rate_limit`, `not_found`, `bad_request`, `timeout`, `network`, `server`, `api`, `bad_model`, `bad_effort`, `refusal`, `max_tokens`, `empty`, `invalid_json`, `unknown`.
- `build_request(...)`: `messages.stream` 인자를 만든다.
  - `cached_context`가 있으면 `system`을 2블록으로 만든다. 첫 블록은 SKILL 본문이며 `cache_control: ephemeral`, 둘째 블록은 호출별 지침이다.
  - `supports_effort`인 모델은 `output_config.effort`와 `thinking: adaptive`를 붙인다. Haiku는 붙이지 않는다.
  - `use_fallbacks`면 베타 `server-side-fallback-2026-07-01`과 `extra_body.fallbacks = "default"`를 붙인다.
- `call_json(api_key, *, model, system, user, schema, max_tokens=16000, effort="high", use_fallbacks=True, cached_context=None, client=None) -> LLMResult`: 스트리밍으로 호출한 뒤 최종 메시지를 검사한다. `stop_reason`이 `refusal`이나 `max_tokens`면 `LLMError`, 텍스트 블록이 없거나 JSON이 아니어도 `LLMError`다. `LLMResult(data, model, request_id, usage)`의 `usage`에는 `input_tokens`, `output_tokens`, `cache_creation_input_tokens`, `cache_read_input_tokens` 중 존재하는 값만 담긴다.
- `check_key(api_key, *, client=None)`: Haiku로 `count_tokens`를 호출해 키를 검증한다. 생성 비용이 없다.
- 스키마 검증은 호출자 몫이다. `client` 인자는 SDK 클라이언트를 대체할 때 쓴다.

### 3.2 generator.py

상수: `MAX_BATCH = 10`, `MAX_ROUNDS = 2`, `MAX_TOTAL = 50`, `DEFECT_ITEMS = A1~A5, B1~B3`.

- `GenRequest(cert, counts, difficulty_mix, topic_scope, points)`: `counts`와 `points`는 유형 이름 키다. `counts`의 입력 순서가 시험지 순서가 된다. `total()`, `to_settings()`.
- `Draft(cert, model, questions, shortfall, log, settings, usage)`: `complete` = 부족분이 없고 문항이 있음.
- `validate_request(req, certs) -> list[str]`: 자격증 선택, 유형 이름, 문항 수 범위(1~50), 배점, 난이도 비율을 검사해 오류 문장 목록을 반환한다.
- `plan_batches(counts)`: 유형 순서대로 슬롯을 펼쳐 10개씩 묶는다.
- `Generator(skills_dir, llm_call, *, effort="high", progress=None, model="")`
  - `run(req) -> Draft`: 생성 컨텍스트를 한 번 만들고 배치마다 `_run_batch`를 실행한다. 마지막에 `토큰 사용` 진행 줄을 남기고, 번호를 1부터 다시 매기며 `points`를 붙인 뒤 스키마를 한 번 더 검증한다. 실패하면 `GenerationError`.
  - `_run_batch`: 최대 `MAX_ROUNDS`회 반복한다. 회차마다 생성 → `_select`(요청 유형·개수 초과분 제거) → `_local_defects`(서식 A1, 동일 질문 B3) → 로컬 결함이 없는 문항만 `_verify`(별도 호출) → 통과 문항 확정, 결함 문항은 결함 사유를 다음 생성 프롬프트에 넣어 다시 생성한다. 마지막 회차 뒤에도 남은 슬롯이 부족분이다.
  - `_verify`: 검증자는 후보를 직접 풀어 `independent_answer`를 적고 결함 코드를 반환한다. 응답이 누락되었거나, 불통과인데 사유가 없으면 A2 결함으로 처리한다(`_verdict_defects`).
  - 조립 단계에서 보기가 있는 빈칸 채우기형의 `options`는 `random.sample`로 섞는다.
  - `log`: 회차별 `{batch, round, topic, type, passed, defects}` 목록이며 시험지에 저장된다.
  - `llm_call`은 `llm.call_json`과 같은 키워드 인자를 받는 호출 가능 객체다. 라우트가 API 키를 바인딩해 넘긴다.
- `save_draft(store, draft, *, accept_shortfall=False)`: 문항이 없거나, 부족한데 수락하지 않았으면 `GenerationError`. 저장 시 `settings`에 `shortfall`과 `usage`를 포함한다.

### 3.3 grader.py

상수: `GRADE_BATCH = 8`, `MAX_TRIES = 3`.

- `Grader(skills_dir, llm_call, *, model, effort="high", progress=None)`
  - `run(attempt) -> GradeOutput(results, overall_feedback, usage)`: 채점 컨텍스트를 한 번 만들고 8문항씩 `_grade_batch`로 채점한다. 이어서 주제별 통계를 코드로 계산해 총평 호출에 넘긴다. 총평이 비면 `GradingError`.
  - `_grade_batch`: 최대 3회 시도한다. 응답을 `_normalize`로 정리한 뒤 `schema.validate_results`와 `score_errors`를 통과해야 한다. 통과하지 못하면 오류 문장을 다음 시도 프롬프트에 넣는다. 3회 모두 실패하면 `GradingError`.
  - `_normalize`: 무응답(`None`, 빈 문자열, 빈 목록)은 코드가 오답·0점으로 강제한다.
- `score_errors(q, r)`: 배점이 있으면 정답 = 배점, 오답 = 0, 부분정답 = 1 이상 배점 미만의 정수. 배점이 없으면 정답 = 1, 오답 = 0, 부분정답 = 0 초과 1 미만.
- 정답은 입력에 없다. `correct_answer`는 채점자가 판단해 반환한다.

### 3.4 schema.py

- `DIFFICULTIES = (상, 중, 하)`, `RESULTS = (정답, 부분정답, 오답)`.
- `validate_question(q, *, expect_blank_answer)`: 필수 필드(`no`, `topic`, `type`, `difficulty`, `question`, `user_answer`), 선택 필드(`options`, `points`), 미허용 필드, 유형별 보기 규칙, `user_answer` 형식을 검사한다. 정답·채점 기준 필드는 허용 목록에 없다.
- `validate_questions(questions, *, expect_blank_answer)`: 번호가 1부터 순차인지도 검사한다.
- `validate_answer(question, answer)`: `None`은 허용, 나머지는 유형의 `answer_ok`로 검사한다.
- `validate_results(questions, results)`: 모든 문항을 정확히 한 번씩 덮는지, `result` 값, 부분정답 허용 유형, 점수 범위, `correct_answer`와 `solution` 존재를 검사한다.
- `compute_stats(questions, results)`: `topic_stats`(주제별 total/correct/partial), 모든 문항에 배점이 있을 때만 `total_score`·`max_score`, 아니면 `None`.
- 검증 함수는 오류 문장 목록을 반환한다. `SchemaError(errors)`는 저장소가 던진다.

### 3.5 qtypes/__init__.py

유형 목록의 단일 출처. `TypeSpec(name, options, answer_ok, answer_hint, option_count, partial_allowed)`를 `REGISTRY`에 등록하고, `QUESTION_TYPES`는 그 키 튜플이다.

| 유형 | 보기 | 답안 형식 | 부분정답 |
|---|---|---|---|
| TrueFalse | 금지 | bool | 불가 |
| 사지선다형 | 필수, 4개 | 정수 1~4 | 불가 |
| 빈칸 채우기형 | 선택 | 문자열 목록 | 가능 |
| 단답형 | 선택 | 문자열 | 불가 |
| 서술형 | 선택 | 문자열 | 가능 |
| 논술형 | 선택 | 문자열 | 가능 |
| 단답형 실습 | 선택 | 문자열 | 불가 |
| 서술형 실습 | 선택 | 문자열 | 가능 |

보기 선택은 있으면 보기형, 없으면 무보기형이다.

### 3.6 storage.py

`Storage(data_dir)`는 `exams/`와 `attempts/`를 만든다.

- ID 형식은 `YYYYMMDD-HHMMSS-xxxx`(`xxxx`는 16진 4자리)이며, 형식이 다르면 `NotFound`다. 경로 조작을 막는다.
- 쓰기는 같은 폴더의 임시 파일에 쓴 뒤 `os.replace`로 교체한다.
- 예외: `StorageError`, `NotFound`(하위 클래스). 파일이 손상되면 `StorageError`이며 목록·집계에서는 건너뛴다.
- `create_exam(cert, questions, *, model, settings, verification_log) -> dict`
- `load_exam(id)`, `list_exams()`: 최신순 요약(`id`, `cert`, `created_at`, `count`, `types`).
- `create_attempt(exam_id, answers, *, elapsed_sec=None) -> dict`: 시험지를 깊은 복사한 뒤 답안을 채우고 검증해 저장한다. 원본 시험지는 바꾸지 않는다.
- `load_attempt(id)`, `list_attempts(exam_id=None)`, `all_attempts()`: 전체 내용을 오래된 순으로 읽는다.
- `save_grading(attempt_id, results, overall_feedback, *, model, usage) -> dict`: 검증 후 `grading`을 덮어쓴다. 같은 응시를 다시 채점하면 이전 결과를 대체한다.

### 3.7 skills.py

호출마다 디스크에서 읽으며 캐시하지 않는다. `CORE_NAMES = (문제 유형, 생성 규칙)`.

- `core_status(dir)`, `list_certs(dir)`(핵심 두 파일을 제외한 `.md` 파일명), `load_core`, `load_cert`(목록에 없는 이름은 `ValueError`).
- `build_generation_context`: 생성 규칙 + 문제 유형 + 자격증 SKILL을 `---`로 잇는다.
- `build_grading_context`: 문제 유형 + 자격증 SKILL.

### 3.8 render.py

- `format_question(text) -> Markup`: 전체를 이스케이프한 뒤 코드 펜스와 인라인 코드만 태그로 바꾸고 줄바꿈을 `<br>`로 바꾼다.
- `format_answer(question, answer)`: 무응답은 `(무응답)`, bool은 참/거짓, 사지선다형은 `N번 보기`, 목록은 ` / `로 잇는다.
- `format_usage(usage)`: `입력 … (캐시 읽기, 캐시 쓰기, 일반) · 출력 … · 캐시 적중 …%`. 입력 합계는 일반 + 쓰기 + 읽기다.
- `suggested_minutes(questions)`: 난이도별 상 20, 중 5, 하 1분의 합.

### 3.9 stats.py

채점된 응시만 집계한다.

- `attempt_rate`: 배점이 있으면 득점/만점, 없으면 문항별 점수 합/문항 수.
- `history_rows`, `trend(rows, limit=20)`, `aggregate(attempts, field)`(정답률 낮은 순), `wrong_items(attempts)`(같은 시험지·문항은 가장 최근 응시만 보고 오답·부분정답을 최신순으로 반환).

### 3.10 jobs.py

`JobRegistry(keep=20)`. `start(target)`이 스레드(daemon)에서 `target(progress)`를 실행하고 `job_id`를 반환한다. `target`은 상태 필드 dict를 반환하며 `update`로 작업에 반영된다. 예외가 나면 `status = "error"`와 `error` 메시지를 기록한다. 이 모듈 밖의 예외는 서버 로그에 상세를 남긴다. `get(job_id)`는 복사본을 반환한다. 작업은 메모리에만 있어 재시작하면 사라진다.

작업 `status` 값: `running`, `done`, `shortfall`, `discarded`, `error`.

### 3.11 keyvault.py

`put(api_key, old_token=None) -> token`, `get(token)`, `drop(token)`. 키는 서버 메모리에만 있고 쿠키에는 무작위 토큰만 둔다. `__repr__`은 키를 노출하지 않는다.

## 4. 라우트

| 메서드·경로 | 핸들러 | 동작 |
|---|---|---|
| GET `/` | main.index | 핵심 SKILL 존재 여부, 자격증 목록 |
| GET `/settings/` | settings.index | 키 보유 여부, 모델 선택 |
| POST `/settings/key` | save_key | `sk-ant-` 접두, 길이 20 이상, 공백 없음을 확인해 `KeyVault`에 저장 |
| POST `/settings/clear` | clear_key | 키 삭제 |
| POST `/settings/test` | test_key | `check_key` 호출 |
| POST `/settings/models` | save_models | 생성·채점 모델을 세션에 저장 |
| GET `/generate/` | generate.index | 생성 폼 |
| POST `/generate/start` | generate.start | 폼 파싱·검증 후 생성 작업 시작 |
| GET `/generate/job/<id>` | job | 진행 화면 |
| GET `/generate/job/<id>/status` | job_status | 진행 상태 JSON(`status`, `progress`, `error`, `exam_id`, `count`, `shortfall`, `log`) |
| POST `/generate/job/<id>/accept` | job_accept | 부족한 채로 저장 |
| POST `/generate/job/<id>/discard` | job_discard | 초안 폐기 |

| GET `/exams/<id>` | solve | 풀이 화면 |
| POST `/exams/<id>/submit` | submit | 답안 변환 후 응시 생성 |
| GET `/attempts/<id>` | attempts.view | 응시·채점 결과 |
| POST `/attempts/<id>/grade` | grading.start | 채점 작업 시작. 이미 채점된 응시는 `regrade=1`이어야 한다 |
| GET `/attempts/<id>/grade/<job_id>` | grading.job | 채점 진행 화면 |
| GET `/attempts/<id>/grade/<job_id>/status` | job_status | 채점 상태 JSON |
| GET `/history/` | history.index | 기록 목록, 추이. `cert` 필터 |
| GET `/history/stats` | statistics | 주제·유형·난이도별 누적 통계 |
| GET `/history/review` | review | 오답 복습. `result`, `topic` 필터, 최대 200건 |

- 생성 폼은 `cert`, `model`, `count_<i>`, `points_<i>`, `mix_<i>`, `topic_scope`를 받고, `i`는 `QUESTION_TYPES`·`DIFFICULTIES` 순서다. 빈 값은 0으로 본다.
- `generate.PRESETS`는 자격증별 문항 수·배점 구성을 담는다(정보보안기사실기: 단답형 12, 서술형 4, 서술형 실습 1과 배점. AZ900: 사지선다형 6, TrueFalse 2, 빈칸 채우기형 2). 생성 화면에서 자격증을 고르면 `static/generate.js`가 값을 채우며, 프리셋이 없는 자격증은 0으로 초기화한다.
- 답안 변환(`exams.parse_answers`): 유형별 형식에 맞지 않거나 비어 있으면 무응답이다. 빈칸 채우기형은 줄 단위 목록이며 뒤쪽 빈 줄을 버린다. 한 항목은 20000자로 자른다.
- API 키가 없으면 생성·채점 시작은 설정 화면 안내와 함께 되돌린다.

## 5. 데이터 형식

저장 위치는 `data/`이며 Git에 포함하지 않는다.

시험지 `data/exams/<id>.json`:

| 필드 | 내용 |
|---|---|
| `id`, `cert`, `created_at`, `model` | 식별·메타 |
| `settings` | `counts`, `difficulty_mix`, `topic_scope`, `points`, `shortfall`, `usage` |
| `questions` | 문항 목록. 정답·채점 기준 없음, `user_answer = null` |
| `verification_log` | 검증 기록 |

응시 `data/attempts/<id>.json`:

| 필드 | 내용 |
|---|---|
| `id`, `exam_id`, `cert`, `created_at`(시험지 생성 시각), `submitted_at`, `elapsed_sec`, `model`(채점 모델) | 식별·메타 |
| `questions` | 문항 사본 + `user_answer` |
| `grading` | 미채점이면 `null`. 채점 후 `graded_at`, `results`, `overall_feedback`, `usage`, `topic_stats`, `total_score`, `max_score` |

문항 필드와 채점 결과 필드의 정의는 `skills/문제 유형.md` 3절, 4.3절이다.

## 6. 호출 흐름

생성: `generate.start` → `JobRegistry.start` → `Generator.run` → 배치마다 (생성 호출 → 로컬 검사 → 검증 호출)을 최대 2회전 → `Draft`. 완전하면 `save_draft`로 저장하고 `done`, 부족하면 `shortfall`로 멈춰 사용자의 수락·폐기를 기다린다. 호출 수는 배치당 최대 4회(생성 2 + 검증 2)다.

채점: `grading.start` → `Grader.run` → 8문항 배치마다 채점 호출(규칙 위반 시 재시도) → 코드가 통계 계산 → 총평 호출 → `save_grading`.

두 흐름 모두 한 작업 안에서 같은 SKILL 본문을 첫 system 블록으로 보내므로 두 번째 호출부터 캐시 읽기가 발생한다. 캐시 최소 길이에 못 미치면 조용히 적용되지 않는다. 확인은 진행 화면의 `토큰 사용` 줄이나 저장된 `usage`로 한다.

## 7. 확장 방법

- 새 자격증: `skills/<이름>.md`를 추가한다. 코드 변경은 필요 없다. 프리셋이 필요하면 `routes/generate.py`의 `PRESETS`에 추가한다.
- 새 문항 유형: `skills/문제 유형.md` 표와 `qtypes/__init__.py`의 `REGISTRY`에 함께 추가한다. 풀이 화면 입력과 `exams.parse_answers`의 분기, `render.format_answer`도 확인한다.
- 새 모델: `llm.MODELS`에 `ModelOption`을 추가한다. effort와 thinking을 지원하지 않으면 `supports_effort=False`로 둔다.
- 검증 회차·배치 크기: `generator.MAX_ROUNDS`, `generator.MAX_BATCH`, `grader.GRADE_BATCH`. `skills/생성 규칙.md`의 문구와 함께 바꾼다.

## 8. 알려진 한계

- 자동 테스트가 없다. 실제 API 호출과 브라우저 화면은 검증되지 않았다.
- `generator.py` 1행 docstring이 "최대 3회"로 남아 있다. 실제 값은 `MAX_ROUNDS = 2`다.
- 작업(`JobRegistry`)과 API 키는 메모리에만 있어 서버를 재시작하면 사라진다. 생성·채점 중 재시작하면 작업이 유실된다.
- 정답을 저장하지 않으므로 채점 결과는 채점 모델의 판단에 의존한다.
- 검증 필터 B(분포·범위)는 배치 단위로만 동작해 시험지 전체의 분포는 보장하지 않는다.
- 단일 사용자·로컬 실행을 전제로 한다. 인증과 동시성 제어는 없다.
